# Native sub-agent asset work

Use this mode when the user or governing instructions authorize delegation and sub-agent tools are available. It works within a running agent session; do not promise worker persistence after the host session ends.

## Implementing agent

1. Search the project library by purpose, synonyms, materials, dimensions and required interactions. Read candidate manifests and inspect promising assets. Reuse a compatible asset that passes the current endpoint criteria directly; record the selection. A retained but deficient recovery candidate is an adaptation input, not a completed delivery. If adaptation is needed, reference the exact source revision and explain the unmet criterion.
2. Write an immutable request file with specs, source references, endpoint, budget and output ownership. Carry through the user's quality target and defining reference features; separate actual user limits from coordinator planning targets. Include a supplied concept or scene image with target description/region using [reference intake](reference-inputs.md); do not require a newly generated concept in every delivery. Supply only relevant context, this skill path and the request path to a worker. Tell it to search the library, resolve references, build/review, save durable evidence and return its location. Set the task boundary explicitly: ordinary fulfillment includes corrections to the requested finish; a first-delivery freeze is only for a requested experiment. Avoid dumping the full parent conversation into every worker.
3. Spawn that bounded asset task; record worker ID. Continue useful scene/proxy work while it runs. Send specification corrections through messages promptly, with a new spec revision for changed requirements. Do not concurrently edit the worker's asset.
4. For an unproven high-fidelity route or prior visual failure, assign one discriminating proof and its return boundary before dependent full finishing. Open the raw primary reference and actual render at comparable object size, including decisive details. Record separate visual and technical verdicts; “better than the last version” is not a visual pass. Return the exact revision, location, observed mismatch, testable next correction and retained good features. Follow up with the same worker at checkpoints; an ended turn does not complete the asset. Use `method_review` when the same leading failure returns after correction: reassess the source, technique and parent instructions before another experiment. Don't freeze an unverified shape or prescribe repeated aesthetic tuning around a local gain. Use already authorized resources; a revision request does not expand paid authorization.
5. Record requester acceptance or outstanding failures separately from worker review and human acceptance. File a versioned library manifest only when its actual status is clear; include searchable purpose/tags, dimensions, parts/interfaces, source/export/preview paths, provenance and limits. Prefer one catalog writer or transactional registration; workers can write isolated candidates.
6. Exercise a later lookup for the finished asset. Reuse/adapt the result rather than generating it again. Do not count a reuse lookup as another new asset.

## Compact maker and reviewer contexts

Use fresh concise contexts for initial makers and independent reviewers when supported; carry forward durable state instead of full conversation forks. Respect any requested model/effort and record actual availability or substitutions. A maker needs the immutable brief, this skill, primary reference bytes/region, relevant project rules, source candidates, owned paths, resource limits and one proof boundary. Do not preload unrelated experiments or a long aesthetic recipe. For a continuing maker, send the changed diagnosis and evidence against the retained revision.

A reviewer needs the brief/reference, anonymous candidate identifiers where useful, actual comparable renders with decisive details, and the relevant endpoint checks. Withhold maker advocacy, cost ranking and prior verdicts until its visual judgment is recorded. Ask for the dominant mismatch, separate visual/function/technical verdicts, retained candidate and one bounded next action. Review the raw images rather than trusting the maker’s summary. Reuse a reviewer for a targeted recheck when context remains useful; a fresh pass can break an entrenched diagnosis, but replacements are not a free route reset. Include all their native usage in the job ledger.

Without authorized delegation, perform the same comparison and decision locally and label it self-review; do not claim independence.

## Worker

Read the skill, request and relevant project rules. Inspect library candidates before generation. Own only the assigned asset and its per-request status/result/evidence files. Use the requested construction endpoint and allocated budget, preserve job IDs, inspect concept/model/export, and send a durable result path plus concise unresolved issues. Record library candidates even when reuse avoids generation. Do not mutate the caller's scene or central catalog without assigned ownership.

Use the project library's manifest schema when provided, including its dimension and cost field names; do not invent incompatible synonyms. Save an immutable revision and compact before-image when requester feedback changes an already reviewed candidate.

Keep compact request/status/result/feedback files so a new worker can resume from the strongest retained result after compaction. Native messages provide communication; these files provide durable evidence. If the caller is idle, a final worker response is still available for its next turn, but autonomous wakeup beyond the host's actual capabilities is not guaranteed.

At a visual checkpoint, publish a compact `checkpoint.json` (or project equivalent) with request/spec/reference hashes, candidate revision, comparison/detail paths, failed criteria and next action. Notify the parent as `review_checkpoint`; do not label it final-ready. Keep the job at `working/review` or `awaiting_requester_review`. The parent records `revise` or `continue` on that revision and promptly resumes the worker using native follow-up. It may continue scene/proxy work between reviews. These are agent decisions within existing authorization, not questions the user must repeatedly answer. A worker may return its turn at the checkpoint; the parent remains responsible for advancing the outstanding request. At a genuine boundary, return `incomplete` with the boundary and strongest candidate; do not substitute a limitations list for completion.

Update durable stage and latest evidence when a bounded experiment ends, before writing a long report. Notify the parent with the frozen preview even when the result fails. The parent updates an established review artifact with the latest evidence and honest status rather than waiting for final delivery. User-requested quiet conversation does not require a stale artifact. Keep records compact; provenance/hashes preserve traceability but do not substitute for visual judgment.

For local resource contention, use a shared project render lock and avoid multiple heavy editor instances. Independent remote waits and lightweight concept/spec work can overlap. Coordination mechanisms should fit the actual host rather than impose a distributed service on a small local task.

At acceptance, require the exact candidate revision actually inspected, not just a matching request ID. A previous result file can remain present while a worker prepares a correction. Wait for its final ready notification and verify revision/paths/hashes before registration; reject stale results before mutating central state.
